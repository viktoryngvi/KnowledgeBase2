memory management
needs to be shared between proceses and hidden from proceses
programs see a vrtual memory index, and the os maps it to the physical memory
restricted mode: maps to virtual memory, x mode meps to physical os
each program believes it has access to the whole memory
process A cannot access process B physical memory pages due to mapping to virtual
virtual address space can be way larger than the physical ram, so many addresses are not mapped to anything (segfault when accessing mmory with no mapping)
a user process cannot access kernel memory

I/O
millions of times slower than a cpu cycle (should not use busy waiting to not hog the cpu)
user request IO (system call)
OS puts the process in a "waiting" state and yields the cpu to another process
when hardware is ready, it sends an interrupt to the cpu
cpu jumps to the interrupt service routine, (pauses what it was doing and immediately switches)
the OS moves the original process back to the ready queue

if nothing arrives from IO then some condition (timeout) will wake the process

authentication
identification: cleiming an identity (username)
verification: proving it (password, biometric, key)

secure storage:
rule 1: the os never stores the passwords in plain text
hashing: the os stores a cryptographic hash of the password.
- on login: inputhash = hash(userinput)
- if inputhash ==  stored password hash, access is granted

cryptographic hash cannot be easily reversed

common vulnerabilities and exploits in OS
os is part of the protected computer base

memory safety:
buffer overflow: C/C++ allowing direct memory manipulation without bound checking
ususlly results in a segfault, but may modify memory of other preceses.
a malicious actor may find ways to exploit this.
fix: allways check memory bounds and user input.
A[9] -> assembly +9 to the index

memory safety
the flaw
 a program allocates a fixed buffer
the os/program fails to check input size allowing writes past the buffer end.

the expliot
attacket overflws the stack to overwrite the return address
cpu jumps to malicious code (shellcode) instead of returning to the main function

mitigation
ASLR randomize mrmory layout so addresses are hard to guess
DEP/NX marks stack memory as "non executable"

--------------------------------------------

race conditions
the OS multitasks so a gap exists between checking file permissions and using it.
check: OS confirms user can write to tmp.txt
The gap: within the gap the user swaps the txt file with a symbolic linc (for example to a password file)
use: OS resumes and gives access to the wrong file
fix: minimize the gap so it cant be exploited

---------------------------------------------

command injection
flaw: passing unsanitised user input directly to a system command
the input gets expanded and potentially run
demo: rm $filename
input: file.txt; rm -rf /

double quotes "$input" around filenames so expansion happens within quotes
double dashes rm -- so anythin after that should be read as a filename, not a flag

File permissions
linux (POSIX model)
every file is owned by a user and a group - user, groups, others
three permissions (bits) - read, write, execute - written as octal form or symbolic - (755) or (rwxr-xr-x)
difficult to give permisions to other users, files can only be assigned to one group.
ACLs on top: fixes the issue, can give any named user/group its own rights

windows (ACL model)
14 different writes types
uses Access Controll Lists, there is no simpler mode underneath
granular, you can assign distinct permissions to different users / groups
inheritence, filer heavily inherit rule from parrent folders
the rights: Full controll, modify, read & execute, list, read, write ...
